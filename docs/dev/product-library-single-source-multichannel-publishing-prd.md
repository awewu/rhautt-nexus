## 1. 本次修订结论

本 PRD 的产品库定位锁定为：

> 一个公共产品事实基座 + 多品牌绑定 + 多渠道只读投影。

因此必须撤回“选择多个品牌后分别写入多个品牌 tenant/品牌产品库”的旧实现和旧口径。

关键结论如下：

1. 产品库不是 Rheem、Ruud、Everhot、Lithnova 各自一份产品库。
2. 新增或编辑一个产品时，只创建或更新一条公共产品主记录。
3. 多品牌适配通过 `product_brand_bindings` 表表达，不复制产品主数据。
4. `brandCode` 是产品与设备品牌的绑定、筛选和展示维度，不是产品数据分区。
5. `tenant_id` 是 Rhautt Comfort 公共产品库实例的技术隔离门牌，遵守 PostgreSQL RLS；不向营销维护人员暴露“多租户”概念。
6. 官网、经销商端和第三方 API 都从统一产品基座读取，再按 `brandCode`、`siteCode`、分类、状态等条件过滤。
7. 官网售价、官网文案、排序、推荐、上下架等属于品牌/站点投影层，可按品牌和站点差异化维护，但默认继承公共产品资料，避免营销人员重复填写。
8. 本期只完善恒热产品数据库和录入/导入闭环，不自动发布到官网；恒热及其他品牌官网现有展示保持不动。

## 2. 背景

当前系统已经具备产品主表、品牌分类树、多语言营销内容、素材引用、官网货架、品牌发布授权和经销商价盘等能力，但产品数据维护仍存在几个问题：

- 产品基础信息、分类、参数、官网文案、素材、价格等字段分散在多个入口。
- 品牌站控制台仍可能让维护人员误以为官网存在另一份产品数据。
- 同一产品的产品事实、营销文案、官网展示和经销商供给边界不够清晰。
- 早期实现中存在按品牌 tenant 写入产品的倾向，不利于第三方统一接口读取。

营销人员真正需要的是：在一个产品库中录入或导入一次产品资料，系统自动形成规范产品档案，并为后续官网、经销商、GEO 和第三方 API 提供统一只读数据基础。

本期不解决官网自动发布问题，先把产品数据库本身做扎实。

## 3. 本期目标

本期目标是完成恒热产品数据库完善阶段，使产品库具备可持续维护、可导入、可核验、可追溯的公共产品基座能力。

本期要做到：

- 支持在当前产品库页面新增、编辑恒热产品。
- 支持恒热物料表的受控导入预检和后续导入提交。
- 支持按产品与 SKU 分离建档。
- 支持同一型号下多个物料/SKU 作为不同配置维护。
- 支持重复型号提示确认，不默认覆盖。
- 支持公共产品记录与一个或多个品牌建立绑定关系。
- 支持官网售价等未来站点投影字段先入库，但本期不驱动官网展示。
- 支持缺失项、冲突、来源行、导入批次和人工处理记录。
- 保证本期产品库变更不会改变任何官网现有展示。

## 4. 非目标

本期明确不做：

- 不自动发布到官网。
- 不切换恒热、Rheem、Ruud、Lithnova 官网现有产品接口。
- 不创建或修改 `site_product_assignments`。
- 不切换 `currentReleaseId`。
- 不退役旧官网接口。
- 不引入产品静态 HTML 生成、SSR 或 GEO 专项渲染。
- 不建设经销商产品副本库。
- 不按品牌 tenant 复制产品主记录。
- 不把 `fact_verified` 等同于官网可见、已发布或可售。

## 5. 核心概念

### 5.1 公共产品主记录

公共产品主记录是产品事实的唯一主档案，保存产品的稳定身份和公共事实，例如：

- 产品名称
- 型号
- 产品类型
- 公共分类
- 生命周期
- 参数
- 资料
- 素材
- 合规证据
- 数据完整度状态

一个现实产品在产品库中应只有一条公共主记录。

### 5.2 SKU / 物料 / 配置

SKU 表达同一产品型号下的销售配置或物料差异。

常见例子：

- 同一型号不同容量
- 同一型号不同包装
- 同一型号不同销售单位
- 同一型号不同物料编码

产品与 SKU 的关系是：

```text
产品 Product
└─ SKU / 物料 / 配置 ProductSku
```

新增产品时必须至少提供一个 SKU 或物料编码。

### 5.3 品牌绑定

品牌绑定表达公共产品与设备品牌之间的关系。

```text
公共产品 Product
├─ Everhot 品牌绑定
├─ Ruud 品牌绑定
└─ Rheem 品牌绑定
```

品牌绑定不是产品副本。它只保存品牌侧需要差异化表达的字段，例如：

- `brandCode`
- `brandModel`
- `normalizedModel`
- `brandDisplayName`
- `status`

唯一规则：

```text
tenant_id + brand_code + normalized_model
```

这表示“同一个公共产品库实例内，一个品牌下同一个规范型号只能绑定一次”。

### 5.4 站点投影

站点投影是官网或其他渠道对公共产品事实的展示规则，不是产品事实来源。

站点投影可包含：

- `siteCode`
- `brandCode`
- 是否展示
- 排序
- 推荐
- 官网售价
- 官网公开路径
- 官网文案覆盖
- SEO/GEO 结构化输出

本期可以预留站点投影字段，但不得驱动官网上线展示。

## 6. 产品身份与重复判断

新增或导入产品时，系统使用以下顺序判断：

1. 规范化型号：`normalizedModel`
2. 读取请求中的 `brandCodes`
3. 在 `product_brand_bindings` 中查找 `tenant_id + brand_code + normalized_model`
4. 命中时提示维护人员确认是否更新已有公共产品并追加/更新 SKU
5. 未命中时创建一条公共产品主记录，并写入品牌绑定
6. SKU 使用 `materialCode` 或 `skuCode` 判断新增或更新

系统不得在命中重复型号时静默覆盖。

系统不得因为选择多个品牌而创建多条产品主记录。

## 7. 恒热导入规则

本期恒热 Excel/CSV 导入规则如下：

1. 只接受受控模板版本。
2. 本期导入入口只允许 `brandCode=everhot`。
3. 其他品牌数据不得通过本期导入入口改变其产品或官网展示。
4. 使用规范化后的 `brandCode + model` 在品牌绑定层判断是否已有产品。
5. 使用物料编码作为 `skuCode/materialCode` 判断 SKU 更新或新增。
6. 同一型号下多个有效物料应合并为一个产品下的多个 SKU，而不是多个产品。
7. 带 `-T` 且名称含“作废”的记录进入排除清单，不作为有效 SKU 导入。
8. 必填字段缺失时，不写入正式产品事实，进入缺失项或冲突处理。
9. 单个产品及其全部 SKU 是原子导入单元；任一关键行失败，整个产品不提交。
10. 重复导入同一份有效数据不得重复创建产品或 SKU。
11. 导入必须记录源文件、模板版本、工作表、源行、源列和操作者。
12. 导入完成后输出新增、更新、排除、失败、缺失字段和人工确认报告。

本期导入结果只进入产品库内部状态，不触发官网或经销商发布。

## 8. 产品库页面要求

当前 `/products` 页面应在现有入口上改造，不新增孤立页面。

新增/编辑弹窗需要支持：

- 选择一个或多个品牌。
- 录入产品名称。
- 录入产品型号。
- 录入 SKU/物料编码。
- 选择产品分类。
- 维护官网参考价、价格展示方式、单位、说明等投影字段。
- 上传主图和资料文件。
- 录入或粘贴官网详情正文。
- 提交前校验必填项。
- 检测重复型号时弹出确认。

多品牌选择时：

- 前端只提交一次。
- 请求中携带 `brandCodes`。
- 后端只保存一条公共产品记录。
- 后端写入多条品牌绑定。

页面提示必须明确：

> 可选择一个或多个品牌；提交后只保存一条公共产品记录，并建立多个品牌绑定。

不得出现“多品牌提交时分别写入各品牌产品库”这类误导性文案。

## 9. 数据模型落点

本期核心表：

| 表                        | 定位                             |
| ------------------------- | -------------------------------- |
| `products`                | 公共产品事实主记录               |
| `product_skus`            | 产品下的 SKU / 物料 / 配置       |
| `product_brand_bindings`  | 产品与品牌的绑定关系             |
| `product_website_pricing` | 官网/站点价格投影                |
| `product_content`         | 产品内容、官网详情、SEO/GEO 输入 |
| `product_import_batches`  | 导入批次                         |
| `product_import_rows`     | 导入源行                         |
| `product_data_issues`     | 缺失项、冲突和质量问题           |

兼容字段说明：

- `products.brand_code` 可作为主品牌提示或历史兼容字段。
- 正式多品牌关系以 `product_brand_bindings` 为准。
- 第三方 API 不应依赖 `products.brand_code` 判断产品唯一归属。

## 10. API 口径

新增/编辑产品请求建议口径：

```json
{
  "tenantId": "<PRODUCT_LIBRARY_TENANT_ID>",
  "brandCode": "everhot",
  "brandCodes": ["everhot", "ruud"],
  "model": "RGS-A",
  "materialCode": "MAT-001",
  "name": "恒热 RGS-A",
  "category": "gas-water-heater",
  "websitePricing": {
    "brandCode": "everhot",
    "siteCode": "everhot",
    "locale": "zh-CN",
    "priceDisplayMode": "show_price",
    "websitePrice": 11800,
    "currency": "CNY",
    "priceUnit": "台"
  }
}
```

重复型号响应：

```json
{
  "code": "PRODUCT_MODEL_EXISTS",
  "resolution": {
    "confirmField": "confirmExistingProduct",
    "confirmValue": true
  }
}
```

维护人员确认后，前端再次提交：

```json
{
  "confirmExistingProduct": true
}
```

## 11. 官网与经销商口径

官网与经销商不保存产品副本。

后续目标接口：

```text
/api/v2/sites/:siteCode/products
```

该接口应从统一产品基座读取，并组合：

- 公共产品事实
- 品牌绑定
- 站点展示规则
- 站点价格投影
- 内容投影
- 素材投影
- 权限和发布状态

本期不启用该接口切换，不改变任何官网页面展示。

## 12. GEO 口径

本期不引入产品静态 HTML、SSR 或 GEO 专项渲染。

后续官网接入阶段再评估：

- 当前浏览器 API 渲染对 AI 抓取器的可见性。
- 是否需要 SSR。
- 是否需要静态产品详情页。
- JSON-LD 是否由产品事实投影生成。

无论采用何种渲染方式，产品事实必须来自产品库，不允许官网手写产品参数。

## 13. 权限与安全

1. 产品写操作只能通过产品库受保护 API。
2. 官网、品牌站运行时和经销商端无产品写权限。
3. 产品库技术层使用公共产品库实例 `tenant_id`。
4. 应用连接使用非超级用户角色，遵守 PostgreSQL RLS。
5. `brandCode` 不得被当作 tenant 隔离边界。
6. 多品牌绑定不得绕过重复型号检查。
7. SKU 已绑定到其他产品时必须阻断，不能自动合并。
8. 删除采用归档或软删除，不物理删除已引用数据。

## 14. 数据状态

本期产品数据库内部状态：

```text
imported_draft -> needs_completion -> fact_verified
```

状态含义：

| 状态               | 含义                             | 对外可见         |
| ------------------ | -------------------------------- | ---------------- |
| `imported_draft`   | 已导入或录入，尚未完成完整性检查 | 否               |
| `needs_completion` | 存在缺失项、冲突或阻断问题       | 否               |
| `fact_verified`    | 指定产品事实版本已核验           | 否，本期仍不发布 |

`fact_verified` 不代表：

- 已发布
- 官网可见
- 经销商可见
- 可售
- 有库存

## 15. 验收标准

### 15.1 公共产品基座

- [ ] 多品牌新增只创建一条 `products` 记录。
- [ ] 多品牌新增写入多条 `product_brand_bindings`。
- [ ] `brandCode + normalizedModel` 唯一性在绑定层生效。
- [ ] 重复型号返回确认提示，不默认覆盖。
- [ ] SKU 已绑定到其他产品时阻断。
- [ ] 第三方/API 消费者可以从统一产品基座读取产品，并按品牌过滤。

### 15.2 恒热导入

- [ ] 受控模板只接受恒热导入。
- [ ] 作废物料进入排除清单。
- [ ] 同一型号多个物料归并为一个产品下多个 SKU。
- [ ] 重复导入不重复建档。
- [ ] 导入预检列出新增、更新、排除、失败和缺失项。
- [ ] 导入提交可追溯到源文件、源行和字段。

### 15.3 官网不变

- [ ] 本期不修改 `site_product_assignments`。
- [ ] 本期不修改 `currentReleaseId`。
- [ ] 本期不触发官网自动发布。
- [ ] 恒热官网现有展示保持不变。
- [ ] Rheem、Ruud、Lithnova 官网现有展示保持不变。

### 15.4 页面体验

- [ ] 在现有 `/products` 页面完成新增/编辑能力。
- [ ] 多品牌文案明确为“公共产品记录 + 品牌绑定”。
- [ ] 新增字段与数据库字段对应。
- [ ] 重复型号时给出明确确认弹窗。
- [ ] 官网售价等字段作为投影字段入库，不驱动官网展示。

## 16. 分阶段计划

### Phase 1：字段与模型基座

- 确认产品、SKU、品牌绑定、官网价格投影字段。
- 完成数据库迁移。
- 完成新增/编辑接口逻辑。
- 完成页面录入字段对齐。

### Phase 2：恒热导入闭环

- 冻结恒热导入模板。
- 完成预检。
- 完成导入提交。
- 完成缺失项、冲突和失败报告。
- 完成代表性样本试导入。

### Phase 3：产品事实核验

- 补齐分类、参数、素材、资料和合规证据。
- 建立完整度检查。
- 建立 `fact_verified` 核验流程。

### Phase 4：官网/渠道接入（后续另行立项）

- 重新评估官网 API、SSR、GEO 和 URL 方案。
- 设计 `/api/v2/sites/:siteCode/products` 正式消费契约。
- 做官网不变性、回滚、缓存和 GEO 验收。

## 17. 最终验收口径

本期以恒热产品数据库完善为最终验收：

> 维护人员能够在当前产品库中新增、编辑或导入恒热产品；系统按公共产品主记录、SKU 和品牌绑定正确建档；重复型号和重复 SKU 有明确提示或阻断；导入过程可追溯、可重试且不重复建档；产品资料可进入 `fact_verified`，但全过程不修改任何官网现有展示、发布状态或渠道消费链路。
